# 接入统一授权平台 —— 适配开发规范

> **读者**：需要把某个新项目接入「统一授权平台（ULP, Unified License Platform）」的开发者或智能体。
> **前提**：ULP 平台已在 **7630** 端口运行，已能签发 `.lic` 授权文件。
> **配套文档**：`03-统一授权文件格式规范.md`（格式的权威定义，**先读它**）、`00-现状调研报告.md`（四个已接入项目的实例参考）。

---

## 0. 五分钟速览

接入一个项目，本质上只做**五件事**：

1. 在你的项目里实现一个 **license 模块**：读文件 → 解析信封 → 验签 → 校验业务字段 → 返回统一状态。
2. 在你的项目里加一个 **门禁**：授权无效时拦截业务请求，但**必须保留恢复通路**。
3. 把 ULP 为你这个项目签发的 **公钥** 放进你的代码或配置。
4. 在你的项目里加一个 **授权上传/查看入口**，让客户能自助换授权。
5. 在你的项目里加一个 **前端门禁**（可选但强烈建议），让用户看到清晰的失效原因和上传入口。

**不要做的**：不要在业务项目里保留签发能力（私钥、签发 CLI、在线生成接口），不要让业务项目在请求路径上访问 ULP。

## 1. 你需要从 ULP 拿到的三样东西

接入前，向 ULP 管理员索取（或在 ULP 的「项目管理」页获取）：

| # | 东西 | 从哪来 | 用途 |
|---|---|---|---|
| 1 | **项目标识 `product`** | ULP 项目管理页新增项目时设定，如 `my-app` | 授权载荷的 `product` 字段，必须与你的代码期望值**完全一致** |
| 2 | **公钥 PEM** | 项目详情页「接入代码片段」/「下载公钥」 | 放在你的代码或配置里，用于验签 |
| 3 | **接入代码片段** | 项目详情页 | ULP 已按 Go / Python / Node 三种语言生成好，可直接抄 |

> **公钥是公开的，可以进代码仓库；私钥绝对不可以。** 私钥只存在于 ULP 服务端（加密存储），永远不下发给你。

## 2. 必须严格遵守的六条不变量

这是整个体系的基石。**任何一条不满足，接入就是不合格的。**

### 不变量 1 · 验签对象是「原始字节」，不是「重新序列化的 JSON」

签名覆盖的是 `data` base64 解码后得到的**原始字节**。验签时必须：

```text
payloadBytes = base64.decode(envelope.data)   # 直接拿字节
crypto.verify(alg, payloadBytes, publicKey, signature)   # 对这些字节验签
# 验签通过之后，才把 payloadBytes 解析成 JSON 对象
```

**绝对不要**这样做（这是本体系中最常见的翻车点）：

```text
# ❌ 错误：解析成对象再重新序列化，字节序可能与签发时不一致
obj = JSON.parse(payloadBytes)
reSerialized = JSON.stringify(obj, sortedKeys)   # 各语言序列化规则不同 → 验签必失败
crypto.verify(alg, reSerialized, ...)
```

**为什么**：Go 的 `json.Marshal` 按结构体字段声明序输出，Python 的 `json.dumps(sort_keys=True)` 按字典序输出，JS 的 `JSON.stringify` 按插入序输出。同一份数据在三种语言下的字节序列**互不相同**。一旦把验签对象改成「重新序列化的结果」，跨语言互验就会全面失效。

**正确顺序永远是：解码 → 验签 → 解析。** 先验签再解析业务字段，还能避免被伪造数据误导业务逻辑。

### 不变量 2 · 通用授权必须显式写 `"*"`，不能用空串

`machine_code` 字段：

| 值 | 含义 |
|---|---|
| `"*"` | **通用授权**，任意机器可用 |
| 其他非空字符串 | 绑定到该机器码，必须与本机计算值一致 |
| 空串 / 缺失 | **无效载荷**，直接判定为 `license_malformed` |

**为什么**：早期版本用「空串 = 通用授权」这一隐式约定。结果是：一份**本应绑定机器**的授权，如果因为 JSON 字段缺失或解析容错而读到了空串，就会被当成通用授权 —— 机器绑定防线**静默失效**，而且看起来一切正常。改成显式 `"*"` 后，缺失字段会被判为损坏格式，故障立刻可见。

### 不变量 3 · 授权失效时，恢复通路必须畅通

**授权无效时，下列入口必须仍然可达**：

- 授权状态查询接口
- 授权文件上传接口
- 授权重载接口（可选但建议）
- 登录 / 鉴权接口（如果系统有登录态）
- 健康检查接口
- 前端静态资源 / 授权页本身

**设计取向**：推荐采用 **「受控前缀 + 强制恢复通路」** 模型（而不是「全部拦截 + 白名单放行」）。

理由：SPA 的前端路由由前端自由定义、数量开放，白名单**无法枚举完整**。一旦漏放行一个静态页面或页面路由，授权到期后客户连登录页都打不开，系统被彻底锁死，只能重装 —— 这是商用授权系统最致命的故障模式。

> ✅ 参考实现：`webb-api-main/webb-api-main/middleware/license.go`（受控前缀 `/api` `/v1` `/v1beta` `/mj` `/pg` `/dashboard` + 恢复通路清单）
> ⚠️ 反面参考：`virtual-employee` 的 `/llm/v1/*` 与 WebSocket 端点因不在 `/api/` 前缀下而**完全绕过**门禁 —— 接入时务必逐条清点你的所有对外入口。

**清点清单**：接入前，列出你的系统**所有**对外提供业务能力的入口（HTTP 路由、WebSocket、gRPC、消息队列消费者、定时任务、CLI 子命令），逐一决定：拦截 / 放行。**只按 URL 前缀粗放地拦截，等于没有拦截。**

### 不变量 4 · 校验默认开启，且初始化失败不得静默放行

- 强制校验开关**默认 `true`**，只有显式设置环境变量才能关闭（开发态调试用）。
- 授权模块初始化失败（公钥解析失败、授权文件损坏、密钥文件不存在）时：
  - **要么拒绝启动**（最安全）；
  - **要么返回 503「服务未就绪」**；
  - **绝不能静默 `c.Next()` 放行**。

> ⚠️ 反面参考：`webb-api/main.go:370-373` 的 `_ = license.Init()` 吞掉了错误，而 `pkg/license/license.go:163-164` 的注释明确写着「返回错误时调用方应当终止启动」—— 注释与实现矛盾，结果是授权模块起不来时系统**无声地失去授权保护**。

### 不变量 5 · 产品绑定必须校验

授权载荷的 `product` 字段必须与你的项目期望值比对，不一致 → `license_product_mismatch`。

**为什么**：统一平台为每个项目独立持有密钥，但密钥轮换、密钥复用、文件误投都可能造成"A 项目的授权被投喂给 B 项目"。产品绑定是防止横向误用的最后一道闸。

### 不变量 6 · 上传安装必须原子化，且坏文件不得覆盖好文件

```
1. 读取上传内容（限大小，如 1 MiB）
2. 完整校验（验签 + 业务字段）
3. 校验通过才落盘：
   a. 备份旧文件为 <path>.bak
   b. 写入 <path>.tmp
   c. os.rename(<path>.tmp, <path>)   # 原子替换
```

**为什么**：客户在授权过期后重新上传授权是高频操作。如果新文件有误却直接覆盖了旧文件，客户会**同时失去**唯一一份可用授权和有效的授权文件，只能重新找厂商补发。校验前置 + 原子替换把这个风险消除。

## 3. 实现参考（四种语言）

### 3.1 Go

```go
import (
    "crypto"
    "crypto/rsa"
    "crypto/sha256"
    "crypto/x509"
    "encoding/base64"
    "encoding/json"
    "encoding/pem"
    "errors"
    "os"
    "time"
)

// Envelope 是 .lic 文件的外层结构。
type Envelope struct {
    Data string `json:"data"` // base64(payload 原始字节)
    Sign string `json:"sign"` // base64(RSA 签名)
}

// Payload 是统一的授权载荷。
type Payload struct {
    SchemaVersion  int       `json:"schema_version"`
    LicenseID      string    `json:"license_id"`
    Platform       string    `json:"platform"`
    Product        string    `json:"product"`
    ProductDisplay string    `json:"product_display"`
    Customer       string    `json:"customer"`
    IssuedAt       time.Time `json:"issued_at"`
    ExpireTime     *time.Time `json:"expire_time"` // nil = 永久授权
    GraceDays      int       `json:"grace_days"`
    MachineCode    string    `json:"machine_code"` // "*" = 通用授权
    InstanceID     string    `json:"instance_id"`
    Features       map[string]any `json:"features"`
}

// Parse 解析并验签。返回 payload 与签名是否有效。
func Parse(raw []byte, publicKeyPEM string) (*Payload, error) {
    var env Envelope
    if err := json.Unmarshal(raw, &env); err != nil {
        return nil, ErrMalformed
    }
    payloadBytes, err := base64.StdEncoding.DecodeString(env.Data)
    if err != nil {
        return nil, ErrMalformed
    }
    sig, err := base64.StdEncoding.DecodeString(env.Sign)
    if err != nil {
        return nil, ErrMalformed
    }
    pub, err := parsePublicKey(publicKeyPEM)
    if err != nil {
        return nil, ErrNoPublicKey
    }
    sum := sha256.Sum256(payloadBytes)                 // ← 对原始字节摘要
    if err := rsa.VerifyPKCS1v15(pub, crypto.SHA256, sum[:], sig); err != nil {
        return nil, ErrBadSignature
    }
    var p Payload
    if err := json.Unmarshal(payloadBytes, &p); err != nil { // ← 验签通过后才解析
        return nil, ErrMalformed
    }
    return &p, nil
}
```

**Go 侧注意**
- `ExpireTime` 用 `*time.Time` 才能表达"永久授权"（`null`）。
- 公钥解析要同时支持 **PKIX（`BEGIN PUBLIC KEY`）** 与 **PKCS#1（`BEGIN RSA PUBLIC KEY`）**。
- 公钥占位符检查：内嵌公钥若是 `REPLACE_WITH_YOUR_PUBLIC_KEY` 之类的占位符，初始化时应直接报错，而不是等到收请求才失败。

### 3.2 Python

```python
import base64, json
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import padding

def parse(raw: bytes, public_key_pem: str) -> dict:
    env = json.loads(raw)
    payload_bytes = base64.b64decode(env["data"])
    signature = base64.b64decode(env["sign"])

    key = serialization.load_pem_public_key(public_key_pem.encode("ascii"))
    key.verify(signature, payload_bytes, padding.PKCS1v15(), hashes.SHA256())
    # ↑ 对原始字节验签；验签通过后才解析
    return json.loads(payload_bytes)
```

**Python 侧注意**
- **不要**用 `json.dumps(obj, sort_keys=True)` 后再去验签（见不变量 1）。
- 若要兼容旧版「内联 JSON 对象 + 规范 JSON 签名」格式，可以写成**双分支解析**：先尝试 base64 解码，失败则回退旧格式。**但新签发一律用统一格式。**
- `cryptography` 库的 `padding.PKCS1v15()` 与 `hashes.SHA256()` 与 Go 的 `rsa.VerifyPKCS1v15(pub, crypto.SHA256, ...)` 完全对应。

### 3.3 Node.js / TypeScript（NestJS）

```typescript
import { createPublicKey, verify } from 'node:crypto';

export function parse(raw: Buffer, publicKeyPem: string): LicensePayload {
  const env = JSON.parse(raw.toString('utf8'));
  const payloadBytes = Buffer.from(env.data, 'base64');
  const signature = Buffer.from(env.sign, 'base64');

  const key = createPublicKey(publicKeyPem);
  const ok = verify('RSA-SHA256', payloadBytes, key, signature);
  if (!ok) throw new BadSignatureError();
  // ↑ 对原始字节验签；验签通过后才解析
  return JSON.parse(payloadBytes.toString('utf8'));
}
```

**Node 侧注意**
- `RSA-SHA256` 对应 Go 的 PKCS#1 v1.5 + SHA-256。**不要用 `RSA-SHA512`**（不兼容）。
- `createPublicKey` 支持 `BEGIN PUBLIC KEY`（SPKI）。若是 PKCS#1 格式的公钥，需要先转换。
- **零第三方依赖**：Node 内置 `node:crypto` 足够，不要为了验签引入 `jsonwebtoken` 之类的库 —— 授权文件不是 JWT，格式是我们自己定义的。

### 3.4 TypeScript（浏览器端 / 前端）

前端**不做验签**（浏览器里的公钥可以被轻易提取，验签没有意义）。前端只做两件事：

1. 调用后端的授权状态接口，展示状态；
2. 后端返回 403 且 code 属于授权类错误时，跳转到授权页。

## 4. 机器码：统一算法与接入要求

### 4.1 算法

```
raw（按优先级取第一个非空值）：
  1. /etc/machine-id
  2. /var/lib/dbus/machine-id
  3. 主机名（hostname）
  4. 首个非回环网卡的 MAC 地址
  5. "unknown"

machine_code = SHA-256("ULP-LICENSE-V1:" + raw) 的前 16 字节
             → 32 位小写十六进制（无分隔符）
```

**要求**：
- 所有接入项目**必须**实现同一算法，否则跨项目的绑定授权无法互换。
- 必须提供**环境变量覆盖**（如 `LICENSE_MACHINE_CODE`），用于容器场景（`/etc/machine-id` 不可读或需要固定值时）。
- 计算结果**建议缓存**（`sync.Once` / `lru` / 模块级变量），因为机器指纹在进程生命周期内不变，而验签在请求路径上会高频调用。

### 4.2 容器环境的注意事项

- Docker 容器内 `/etc/machine-id` 通常**存在但可能为空**（或与宿主机相同）→ 必须走完整个 fallback 链，且**不要**在容器内假定 hostname 唯一。
- 若同一台宿主机运行多个实例且需要区分绑定，建议在 compose 中显式设置 `LICENSE_MACHINE_CODE`。
- **注意**：如果你的指纹完全由容器内可变的量（如容器 ID）构成，客户在容器重建后会失去授权 —— 绝不要用容器 ID。

### 4.3 兼容期建议

若你的项目已有旧版机器码算法（格式不同），可在过渡期**同时接受**新旧两种格式：
```
if payload.machine_code == "*"                     -> 通用授权，放行
if payload.machine_code == unifiedMachineCode()    -> 匹配，放行
if payload.machine_code == legacyMachineCode()     -> 兼容期匹配，放行（并记录告警）
else                                               -> license_machine_mismatch
```

## 5. 统一状态码词表

**必须原样使用这些字符串**，前后端、跨项目都要一致。

| 状态码 | 含义 | 授权是否有效 | 建议的用户引导 |
|---|---|---|---|
| `ok` | 授权有效 | ✅ | — |
| `license_grace` | 已到期，但在宽限期内 | ✅ | 提示续期（醒目但不阻断） |
| `license_disabled` | 校验未启用（仅开发态） | ✅ | — |
| `license_not_init` | 授权模块未初始化 | ❌ | 提示服务未就绪 |
| `license_missing` | 找不到授权文件 | ❌ | 引导上传授权文件 |
| `license_malformed` | 文件结构或编码损坏 | ❌ | 引导重新上传 |
| `license_bad_signature` | 签名校验失败 | ❌ | 提示文件被篡改或非本平台签发 |
| `license_expired` | 已到期且宽限期结束 | ❌ | 引导续期 |
| `license_clock_rollback` | 检测到系统时间回拨 | ❌ | 提示校准系统时间 |
| `license_machine_mismatch` | 授权与本机不匹配 | ❌ | 提示授权绑定了其他机器 |
| `license_product_mismatch` | 授权的项目与当前程序不符 | ❌ | 提示授权文件用错项目 |
| `license_no_public_key` | 内置公钥未配置或仍是占位符 | ❌ | 提示构建产物未替换公钥 |

**若你的项目原本已有自己的状态码词表**（如 `LICENSE_EXPIRED` / `license_expired` 混用），在迁移期做**双向映射**，并在 UI 上只显示统一词表的那一套。

## 6. 后端 API 契约

统一约定以下四个接口（路径前缀可按你的项目调整，但**语义与响应结构必须一致**）：

| 方法 | 路径 | 用途 | 是否受门禁保护 |
|---|---|---|---|
| GET | `/api/license/status` | 查询当前授权状态 | ❌ 永远放行 |
| GET | `/api/license/machine-code` | 查询本机机器码（供客户填写到 ULP） | ❌ 永远放行 |
| POST | `/api/license/upload` | 上传授权文件（multipart，字段名 `file`） | ❌ 永远放行 |
| POST | `/api/license/reload` | 强制重新读取授权文件 | ❌ 永远放行 |

**状态响应体**（统一结构）：

```json
{
  "code": "ok",
  "valid": true,
  "message": "授权有效，到期时间 2027-10-27 19:26",
  "in_grace": false,
  "remaining_days": 365,
  "checked_at": "2026-10-27T11:26:00Z",
  "license": {
    "license_id": "a1b2c3...",
    "product": "my-app",
    "product_display": "我的应用",
    "customer": "某某有限公司",
    "issued_at": "2026-10-27T11:26:00Z",
    "expire_time": "2027-10-27T11:26:00Z",
    "grace_days": 7,
    "machine_code": "*",
    "instance_id": "",
    "features": {}
  }
}
```

**要点**
- `GET /status` 在授权无效时仍返回 **HTTP 200**，用 `valid: false` + `code` 表达失败 —— 这样前端能拿到具体原因，而不是一个无信息的 403。
- `POST /upload` 校验失败时，同样返回 **HTTP 200**（若你的项目统一用 `success: false` 契约，则用它）+ `code` + `message`，让前端直接展示原因。
- 门禁拦截时返回 **HTTP 403**，响应体必须包含 `code` 字段，前端靠它识别"这是授权问题"并跳转。

**⚠️ 常见陷阱**：前端拦截器里的错误码判据必须与后端实际返回的**完全一致**。已知反面案例：后端返回 `license_*`，前端判据写成 `startsWith('LIC_')` → 跳转永不触发，用户只看到裸 403。**接入后务必端到端验证一次"授权到期 → 是否自动跳到授权页"。**

## 7. 前端门禁

推荐做，且要做对。

### 7.1 最小可用形态

```
应用启动
  → 请求 GET /api/license/status
  → valid === true  → 正常渲染
  → valid === false → 全屏渲染授权页（LicensePage）
```

授权页需要包含：
- 当前状态码与人类可读的原因
- 客户名、到期日期、剩余天数（若有）
- 文件选择器（`accept=".lic,application/json"`）
- 上传按钮 → `POST /api/license/upload` → 成功后重新请求状态并放行
- "重新检测"按钮（重新拉状态）

### 7.2 全局 HTTP 拦截器

后端返回 403 且 `code` 属于授权类错误时，前端应跳转到授权页。注意：
- 跳转要**避免死循环**（在授权页上不要再触发跳转）。
- 授权相关接口本身要**跳过**该拦截逻辑。
- 多语言项目要同步准备 i18n 文案。

### 7.3 门禁的覆盖范围要匹配后端

如果后端门禁只拦 `/api/*`，那前端门禁必须覆盖**所有页面路由**；反之如果后端拦了全部业务入口，前端门禁可以只做状态展示。**两者范围不一致就会出现"页面能打开但点什么都 403"的割裂体验。**

## 8. 时间回拨防护

授权到期是靠时间判断的，因此**系统时间回拨**是最常见的绕过手法。

### 8.1 基本做法

维护一个"上次见到的时间"检查点文件：

```
last = 读取检查点（若存在）
if last != nil && now + 容差 < last:
    → license_clock_rollback
if last == nil || now > last:
    → 写入 now（仅在时间前进时写，保证单调）
```

**容差**建议 5~10 分钟 —— 用来容忍 NTP 校时、虚拟机时钟漂移；真正要拦的是"把时间往回调几个月"。

### 8.2 进阶：检查点加 HMAC

裸 JSON 检查点文件是可以被客户手工编辑伪造的。给检查点加一个 HMAC：

```
body = "<unix秒>|<hex(HMAC-SHA256(secret, unix秒))>"
```

读取时 HMAC 不匹配 → 视为"无历史基准"，**不误判为回拨**（当作首次运行），同时可记录告警。

> 参考实现：`webb-api-main/webb-api-main/pkg/license/license.go:494-530`（`readClock` / `writeClock` / `clockMAC`）

### 8.3 注意事项

- 检查点文件必须在**持久化卷**里（容器重建后仍存在），否则重建即丢失基准。
- 检查点的读写要在**同一把锁内**原子完成，避免并发请求的微小时间差被误判为回拨。
- **永久授权也必须参与回拨检测** —— 否则把系统时间调回去就能让永久授权"续命"。

## 10. 常见错误与排查

| 现象 | 最可能的原因 | 排查方法 |
|---|---|---|
| 验签总是失败，但文件确实由平台签发 | **验签对象用了重新序列化的 JSON**（不变量 1） | 打印待验签字节的 hex，与签发端比对 |
| 验签在 Go 成功、在 Python 失败（或反之） | 同上，跨语言序列化字节序不同 | 同上 |
| 授权有效但机器码不匹配 | 各项目实现了不同的机器码算法 | 比对 §4.1 的前缀 `"ULP-LICENSE-V1:"` 与哈希截断长度（16 字节 / 32 hex） |
| 授权到期后前端不跳转，只显示裸 403 | 前端错误码判据与后端不一致 | 直接抓包看 403 响应体里的 `code` 实际值，与前端判据逐字比对 |
| 授权有效但显示"状态未知" | 前端状态标签 switch 的取值集合与后端词表零交集 | 以后端实际返回的 `code` 为准重写映射 |
| 容器重建后授权失效 | 授权文件没落在持久化卷 | 检查 compose 的 volumes 挂载点是否覆盖授权文件路径 |
| 客户改系统时间后授权"续命" | 未实现或未启用回拨检测 | 检查检查点文件是否写在持久化卷，且确实参与判断 |
| 授权模块起不来但系统照常提供服务 | 初始化错误被吞（不变量 4） | 启动日志里加致命日志 + 拒绝启动 |
| 客户上传新授权后反而全坏了 | 上传未做校验前置 / 非原子替换（不变量 6） | 上传先校验再落盘；确认旧文件有 `.bak` 备份 |
| 未授权仍能调用核心能力 | 有入口不在门禁覆盖范围内（不变量 3） | 逐条清点所有对外入口，别只按 URL 前缀粗放拦截 |
| WebSocket / gRPC 能绕过授权 | 只拦了 HTTP | 为 WS / gRPC 补上等价的校验 |
| 授权显示有效但功能被限 | 后端门禁和前端门禁范围不一致 | 对齐两者的覆盖范围 |

## 12. 版本与兼容性

| 项 | 值 |
|---|---|
| 授权文件 schema 版本 | `schema_version: 1` |
| 签名算法 | RSA-2048 / PKCS#1 v1.5 / SHA-256 |
| 外层信封 | `{"data": <base64>, "sign": <base64>}` |
| 签发方标识 | `platform: "unified-license-platform"` |
| 机器码前缀 | `"ULP-LICENSE-V1:"` |
| 状态码词表 | 见 §5 |

**向前兼容规则**
- 验签方在解析出 payload 后，**忽略未知的额外字段**（不要因为多了一个字段就报格式错误）。
- 验签方遇到未知的 `schema_version`（> 当前支持版本）时，应拒绝并给出明确原因，而不是尝试按旧规则解析。
- 平台签发时，`schema_version` 必须显式写入。
